# AI Native 项目运行机制 V1.0

> 状态：V1.0 基础架构定义  
> 适用范围：当前项目及后续可复用项目  
> 核心原则：先跑通项目，再根据真实运行结果迭代机制；Git 作为项目资产底座，不单独建设项目管理平台。

## 0. V1.0 知识库结构与唯一事实来源

本文件是 `ai/knowledge-base/v1.0/` 的**核心源知识库**，用于记录本项目 AI Native 运行机制、已确认规则、关键决策和可复用原则。

- `AI_NATIVE_PROJECT_OS_V1.0.md`：核心源知识库，AI 执行时优先读取
- `PROJECT_DIRECTORY_NOTE.md`：Git 项目目录说明，仅保留目录归属与导航信息，不重复业务规则
- `project-evolution/`：记录本项目如何从实际问题逐步演进到当前完整 AI Native 流程，不替代当前规则
- `decisions/`：记录单个关键决策及其依据、影响和生命周期
- 迭代总结文档：面向项目成员阅读的交付物，不作为 AI 的第二事实来源

后续如其他文档与本文件存在重复：**以本文件为准**；新增规则应回写本文件，避免同一规则在多个文件中维护不同版本。

## 1. 这套体系要解决什么问题

本项目不是为了建设一个新的项目管理平台，而是验证一套可以真实运行的 AI Native 项目机制：

**持续感知 → 问题/机会识别 → AI 分析 → 决策 → Product → Design → Engineering → QA → Release → 结果验证 → 知识沉淀 → 能力复用 → 下一轮迭代。**

最终目标不是单纯“让 AI 帮人做更多事情”，而是逐步让项目具备：

- 更高的执行效率
- 更稳定的交付质量
- 更高的资产复用率
- 更高的自动化程度
- 可持续学习和自我迭代能力

## 2. 项目基础架构

### 2.1 项目层级

项目采用：

**项目 → 业务域/模块 → 事项 → 阶段 → 任务 → 执行记录 → 交付资产**

Git 文件夹负责资产存储，不代替业务层级。事项通过唯一 ID 与 Product、Design、Engineering、QA、Release、Knowledge 等资产建立关联。

### 2.2 Project Hub 与 Git 边界

Project Hub 是项目统一入口，用于展示项目结构、当前状态、事项关系及直接访问 Git 资产；不把它扩展为独立项目管理平台。Git 已经承担项目资产、版本和部分项目管理工作。

### 2.3 项目资产

- `ai/`：AI、Knowledge Base、Rules、Workflows、Agents
- `product/`：Product 需求与研究
- `design/`：UX/UI
- `engineering/`：工程与架构
- `src/`：实际前端代码
- `qa/`：测试与质量保障
- `release/`：发布与版本
- `analytics/`：数据分析
- `docs/`：项目文档
- `plugin/`：插件相关内容

## 3. 项目执行记录

每个重要节点应记录：

- 事项 ID
- 当前阶段
- 负责人
- 参与人
- AI 是否参与
- AI 完成/辅助内容
- 开始时间
- 计划结束时间
- 实际结束时间
- 计划耗时
- 实际工作耗时
- 等待耗时
- 自然周期
- 返工次数
- 变更次数
- 阻塞原因
- 交付资产
- 上下游依赖

### 3.1 时间口径

必须区分：

- **自然周期**：从开始到结束的日历时间
- **实际工作耗时**：人员/AI 真正投入工作的时间
- **等待耗时**：等待确认、依赖、数据、接口等造成的时间

避免把“4 天完成”直接等同于“工作了 4 天”。

## 4. 持续迭代驱动层

V1.0 已确认的持续迭代驱动源：

### 4.1 竞品

用于感知外部市场、竞品能力、交互及行业变化。

输出：竞品变化 → 机会/风险 → 产品判断。

### 4.2 数据

用于感知产品真实使用情况、行为变化、异常和问题。

输出：数据变化 → 诊断 → 问题/机会。

### 4.3 KPI

用于判断业务目标是否达成。

输出：目标 → KPI → 实际结果 → 差距 → 原因 → 优化。

### 4.4 用户反馈

**状态：待建设。**

当前项目尚无正式用户反馈入口，因此 V1.0 先定义能力，不阻塞当前项目运行。未来应支持：采集 → 分类 → 聚类 → 影响评估 → 与数据/KPI/竞品交叉验证 → 进入 Product。

后续可按实际需要增加其他驱动源，例如技术能力变化、项目经验与效率数据等。

## 5. 什么叫“自闭环”

本项目中的自闭环特指**自动化执行闭环**，而不是单纯的流程闭环。

目标路径：

**发现 → 分析 → 决策建议 → 执行 → 验证 → 学习 → 再执行。**

AI 应逐步从辅助执行升级到自动分析、自动执行、自动验证和自主迭代；人工只在必要的决策门介入。

## 6. 自动化闭环机制

### 6.1 Trigger / 触发器

每类持续迭代信号都应具备明确触发条件，例如：

- 竞品发生重大变化 → 自动触发竞品分析
- KPI 低于目标阈值 → 自动触发 KPI 诊断
- 数据出现异常 → 自动触发数据分析
- 用户反馈达到聚类/影响阈值 → 自动触发反馈分析（待建设）

### 6.2 AI 分析

AI 根据当前任务上下文、知识库、数据、竞品信息及 KPI 进行分析，并输出问题/机会、证据和置信度。

### 6.3 决策门 Human Gate

不同事项设置不同自动化等级：

- AI 自动执行
- AI 生成方案 → 人工确认
- AI 分析 → 人工决策
- 必须人工决策

核心业务规则、重大范围变化、正式发布等高风险节点必须保留人工决策门。

### 6.4 自动执行

经授权的事项由对应 Workflow / Agent 执行，并记录输入、决策、修改内容、执行版本及影响范围。

### 6.5 自动验证

执行后必须验证结果：

- KPI 是否改善
- 数据是否恢复/改善
- 质量是否达标
- 是否产生副作用

结果应进入：保留 / 回滚 / 重试 / 重新分析。

## 7. 自动检测机制必须标注来源

这是 V1.0 的明确要求：**任何自动检测、自动诊断、自动触发都必须记录证据来源，不能只输出结论。**

建议统一使用以下 Source / Evidence 结构：

```text
Detection ID
检测类型
检测时间
触发条件
来源类型
来源地址/路径
来源版本/时间范围
原始证据摘要
计算/判断方法
检测结果
置信度
关联事项 ID
后续动作
```

### 7.1 来源类型

至少支持：

- `competitor`：竞品来源
- `analytics`：数据分析来源
- `kpi`：KPI/指标来源
- `user_feedback`：用户反馈来源（待建设）
- `knowledge_base`：项目知识库
- `github`：代码、Issue、PR、Commit 等 Git 来源
- `design`：设计资产
- `product`：Product 文档
- `engineering`：工程/技术资产
- `qa`：测试结果
- `release`：发布结果

### 7.2 来源标注原则

自动检测结果至少能够回答：

1. **从哪里发现的？**
2. **什么时候发现的？**
3. **依据是什么？**
4. **使用了哪个版本/时间范围的数据？**
5. **为什么得出这个判断？**
6. **最终关联了哪个项目事项？**

这样 AI 的自动化行为可以被审计、复现和追溯。

## 8. Context Readiness / 上下文就绪度

AI 执行前先判断是否拥有足够上下文：项目目标、当前事项、Product、Knowledge Base、Design、数据/KPI、约束条件和上下游依赖。

缺失关键上下文时，AI 不应自行猜测并继续执行，而应暂停并提出补充信息请求。

## 9. 依赖与影响分析

事项之间建立上下游关系，例如：**REQ → DES → ENG → QA → REL**。

当 Product、业务规则、KPI 或其他关键资产发生变化时，应能够识别受影响的 Design、Code、QA、Workflow 和 Knowledge。

## 10. 版本、回滚与可追溯

每次 AI 执行至少记录：执行版本、执行时间、Agent / Workflow、输入上下文、使用的来源、AI 判断、AI 决策、修改内容、影响范围和验证结果。重要自动变更必须支持回滚。

## 11. 知识自闭环

项目执行不是终点：

**项目执行 → 决策 → 交付 → 测试 → 结果 → 问题 → 经验 → Knowledge Base → 下一次执行。**

Knowledge Base 不只记录成功经验，还必须记录：已确认结论、Decision Log、Change Log、最佳实践、失败经验、已否决方案、适用条件和不适用条件。

## 12. 项目复用闭环

项目资产应逐步形成可复用能力：Product 模板、Design 模式、业务规则、技术方案、QA 用例、Workflow、Agent、Prompt/规则、失败案例。

复用能力至少记录：复用次数、复用项目数、节省工时、成功率、修改率和复用后的效果。

## 13. 能力地图

建立项目级 AI 能力地图，用于知道当前已经具备哪些能力，以及每项能力的自动化等级、稳定性、复用情况和应用项目。

自动化等级建议：

- L0：人工
- L1：AI 辅助
- L2：AI 自动分析
- L3：AI 自动执行
- L4：AI 自动验证
- L5：AI 自主迭代

## 14. 效率与 ROI

V1.0 记录效率，但当前阶段不预设具体提升目标。后续可比较人工工时、AI 工时、AI 成本、总成本、项目周期、等待时间、返工次数、交付质量、自动化率、复用率和 ROI。

效率对比应尽量使用同类、相近复杂度任务，避免直接用不同任务做简单横向比较。

## 15. 目标层

KPI 不是唯一的目标表达。项目应区分：**项目目标 → 阶段目标 → KPI → 任务。**

AI 做任务判断时，应优先检查任务是否服务于当前目标，而不是只判断任务能否完成。

## 16. 当前项目边界

当前重点是**先把 AI Native 项目运行机制在科室挂号项目中跑通**，而不是建设独立项目管理平台。

Git 已经承担项目资产、版本和部分项目管理工作；Project Hub 负责统一导航与上下文入口即可。

## 17. 当前项目业务上下文

本次项目核心业务模型为：**城市 → 医院 → 院区 → 科室 → 医生 → 日期/号源 → 挂号**。

当前阶段属于能力建设阶段，暂不指定具体提升指标；单院区医院可跳过院区选择。

前台用户端与后台管理端保持独立；当前预览如果出现后台管理界面，不代表项目整体定位变为后台项目。

## 19. Project Evolution：完整演进过程

本项目需要保留“我们如何从实际问题逐步形成完整 AI Native 流程”的演进记录。这里记录的是**可审计的项目思考、问题发现、方案演进和决策过程**，不是模型隐藏的 Chain-of-Thought。

完整过程单独记录于：

`ai/knowledge-base/v1.0/project-evolution/EVOLUTION-001-AI-NATIVE-PROJECT-FLOW.md`

演进主线：

**Git 项目资产 → 项目目录结构 → 项目层级 → Product/Design/Engineering/QA → 人员与时间 → 效率衡量 → Knowledge Base → 知识自闭环 → 项目复用 → 竞品/数据/KPI 持续驱动 → 用户反馈待建设 → 自动化自闭环 → Trigger → AI 分析 → Human Gate → AI 执行 → 自动验证 → 回滚/重试 → Knowledge Update → 能力持续进化。**

Project Evolution 与当前规则的关系：

- Evolution 回答“**我们怎么走到这里**”
- Decision Log 回答“**某个关键节点为什么这样决定**”
- 本文件回答“**当前应该怎么运行**”

三者互补，但**当前规则仍以本文件为唯一事实来源**。

## 20. Project Context Persistence / 项目上下文持久化规则

Project Context 是**项目生命周期级上下文**，不是某个 Stage 的临时 Input。Project Initialization 负责创建/刷新 Project Context；后续所有 Agent 必须优先复用它。

### 20.1 Input Source Priority

Agent 执行阶段输入按以下优先级解析：

1. **Project Context**：项目名称、目标、范围、版本、仓库、分支、运行环境、Workspace 等已确认基础信息。
2. **Previous Stage Output**：上游阶段已经确认并交付的结果。
3. **Knowledge Base**：已沉淀且适用的规则、决策、经验和模板。
4. **User Input**：仅用于补充前三层仍缺失的必要信息，或明确覆盖已有值。

### 20.2 Context Reuse Rule

任何 Agent 在向用户询问前，必须先检查 Project Context、Previous Stage Output 和 Knowledge Base。已存在且仍有效的信息不得重复询问。

用户明确修改某项信息时，以本次明确输入为最新值，并同步更新 Project Context 与相关记录。

### 20.3 Missing Input Rule

只有在缺失信息属于当前阶段的 **Required Input** 且无法从已有资产解析时，才允许请求补充。非阻塞缺失不得阻断已具备条件的工作。

### 20.4 Resume / Handoff Rule

`继续 [Stage]`、阶段切换和 Agent Handoff 均必须恢复已有 Project Context，不要求用户重新提供已经确认的项目基础信息。

### 20.5 Execution Continuity Rule

同一问题如果第一次无法解决，应明确记录 Blocked 原因和缺失项；不得通过重复询问相同信息形成循环。连续阻塞应触发 Review / Evolution 记录，并沉淀为 Knowledge Rule。

### 20.6 Persistence Requirement

凡本轮新确认的项目级信息、阶段状态、关键决策和执行结果，应在阶段完成后写回对应项目资产，使下一轮 Agent 可以直接复用。

本规则来源：`EVOLUTION-010-PROJECT-CONTEXT-PERSISTENCE.md`、`EVOLUTION-011-EXECUTION-CONTINUITY-REVIEW.md`。
